## Description
Implement backend support for PayPal Smart Buttons on the frontend - the one-click PayPal checkout experience.

## Acceptance Criteria

### Additional Endpoints

#### Capture PayPal Order
- [ ] `POST /api/v1/payments/paypal/capture`
- [ ] Called by frontend after user approves in PayPal popup
- [ ] Captures the approved order

### Request Body (Capture)
```json
{
  "order_id": "5O190127TN364715T"
}
```

### Response Format (Success)
```json
{
  "success": true,
  "data": {
    "transaction_id": "TXN-123456",
    "amount": 10.00,
    "credits": 10.50,
    "new_balance": 35.50
  }
}
```

### Controller Implementation
- [ ] `capturePayPalOrder()` method in PaymentController
- [ ] Validates order belongs to user
- [ ] Calls PayPalGatewayService->capturePayment()
- [ ] Calls CreditService->addCredits() on success
- [ ] Updates transaction status

### Validation Rules
- [ ] `order_id` required
- [ ] Order must belong to authenticated user
- [ ] Order must be in 'approved' state (not already captured)

### Error Responses
- [ ] 400 Bad Request if order already captured
- [ ] 401 Unauthorized if order belongs to different user
- [ ] 404 Not Found if order doesn't exist
- [ ] 422 Unprocessable Entity for validation errors

### Frontend Integration Notes
- [ ] PayPal SDK loads on frontend
- [ ] Frontend calls create order endpoint
- [ ] PayPal popup handles authentication
- [ ] Frontend calls capture endpoint on approval

### Feature Tests
- [ ] Test successful capture
- [ ] Test double capture prevention
- [ ] Test wrong user capture prevention
- [ ] Test already captured order handling
- [ ] Test unauthenticated returns 401

## Dependencies

- TASK-26-13 (create order endpoint)

## Effort Estimate
`Small` (2-3 hours)

## Notes
- Smart Buttons provide better UX than redirect flow
- Order must be captured within time window (typically 3 hours)
- Consider implementing both popup and redirect flows

## Security Considerations
- Verify order ownership before capture
- Prevent double capture
- Validate order state before capture
- Log all capture attempts

**Key Implementation Changes:**
1. **Fixed Credit Addition Flow:**
   - Removed CreditService dependency for balance updates
   - Directly updates Credit model within DB transaction
   - Creates Credit record if missing (for new users)
   - Updates `total_purchased` along with `balance`

2. **Why CreditService Wasn't Used:**
   - CreditService has idempotency check for `payment_provider` + `payment_id`
   - PayPal Order endpoint creates pending transaction with same `payment_id`
   - Capture endpoint needs to update existing transaction, not create new one
   - Direct repository/model approach avoids idempotency conflict

3. **Flow:**
   - Find pending transaction by order_id (with lockForUpdate)
   - Verify ownership (IDOR prevention)
   - Check order status (must be 'approved')
   - Check expiration (3 hour window)
   - Call PayPalGatewayService->capturePayment()
   - Update Credit balance directly
   - Update transaction metadata with 'completed' status

4. **Security Features:**
   - Order ownership verification (IDOR prevention)
   - Double capture prevention (status check + lockForUpdate)
   - Order expiration check (3 hour window)
   - Audit logging for all capture attempts
