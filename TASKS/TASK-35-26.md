# TASK-35-26: Fix Production SPA Auth Persistence for Local SEO Protected Routes

## STATUS
`To Test Locally`

## SPECIFICATION
SPEC-035: Local SEO & Google Business Profile Tracking

## PRIORITY
`High`

## RISK
`Medium`

## Description
Repair the production authentication contract used by the frontend Local SEO flow. The production host now correctly serves `/sanctum/csrf-cookie` and `/api/v1/auth/*`, and `POST /api/v1/auth/login` returns **200 JSON** with the expected user payload plus a bearer token. But the same browser session remains unauthenticated on `GET /api/v1/auth/user`, so the SPA cannot stay logged in for protected routes like `/sites/{siteId}/local`.

## Acceptance Criteria
- [ ] The production browser login flow establishes a usable authenticated state for the SPA.
- [ ] After browser-based login or registration, a same-session `GET /api/v1/auth/user` returns **200 JSON** for the authenticated user rather than `401 {"message":"Unauthenticated."}`.
- [ ] The frontend auth context can survive navigation to protected routes without immediately clearing the stored user state.
- [ ] `/sites/{siteId}/local` can remain accessible after real login instead of bouncing back to `/login` because `fetchUser()` fails.
- [ ] The chosen auth contract is consistent end-to-end: either proper Sanctum/session-cookie auth works for the SPA, or the documented localStorage/bearer fallback is fully implemented and used by protected frontend fetches.
- [ ] Login/logout/register behavior is covered by automated tests for the chosen auth mode.
- [ ] Deployment/configuration notes are updated if the production auth mode changes.

## Dependencies
- TASK-25-17 (Frontend Auth Context & Provider)
- TASK-35-25 (Fix Production API Routing for Authenticated Local SEO Flow)

## Effort Estimate
3 hours

## Technical Notes
- `frontend/lib/api/auth.ts` uses `credentials: "include"` and assumes the browser session will authenticate `GET /api/v1/auth/user` after login/register.
- In production on 2026-03-10, browser-like login returned **200 JSON** with a bearer token, but the same browser session still got **401 JSON** from `/api/v1/auth/user`.
- `AuthContext` stores `seoindicator_user` locally, but initialization calls `fetchUser()` and clears local auth if the API still reports the session as unauthenticated.
- This mismatch blocks all protected Local SEO browser validation, even before the locations API bug is addressed.
