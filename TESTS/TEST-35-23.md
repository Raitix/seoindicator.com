## Scope
Design red-phase frontend coverage for the Local SEO alerts experience, including:
- global alerts workspace for all user locations
- compatibility route shells for location-scoped dashboard entry points
- alert cards, detail modal, unread badge, and toast notifications
- filter controls for severity, type, read/unread, and location scope
- unread-count and mark-as-read UX against the TASK-35-16 API contract

## Route Design Decision
The task acceptance criteria explicitly require `/local-seo/alerts`, but the existing local dashboard link builder already targets:
- `/locations/[id]/alerts`
- `/sites/[siteId]/local/[locationId]/alerts`

To avoid breaking the shipped dashboard contract while still satisfying the specification, this test package covers:
1. **primary global route** `/local-seo/alerts`
2. **scoped compatibility shells** that can either:
   - render the same alerts workspace with a pre-applied location filter, or
   - redirect to the global route with equivalent query params

## Coverage Matrix

### Route Shells
- Global route renders all-locations alerts workspace with no scoped ids.
- `/locations/[id]/alerts` passes the location id as an initial filter.
- `/sites/[siteId]/local/[locationId]/alerts` passes both site and location ids.

### Workspace Page
- Renders heading, unread badge, filters, cards, and pagination summary.
- Shows back-to-dashboard link when invoked from scoped dashboard context.
- Persists filter changes through the alerts hook input contract.
- Opens detail modal from a selected alert.
- Marks a single alert as read.
- Marks all alerts as read from the header action.

### Alert Card
- Shows severity badge, icon, title, message, location link, relative time, and unread indicator.
- Opens detail view from the card body.
- Calls the mark-as-read callback for unread alerts.

### Detail Modal
- Displays full alert title/message/location/timestamp.
- Displays related data rows when alert metadata exists.
- Exposes a quick-action link for the affected workspace.
- Allows mark-as-read directly from the modal.

### Unread Count Badge
- Hides when zero by default.
- Uses `role="status"` + `aria-live="polite"`.
- Escalates visual tone when critical alerts are unread.

### Alert Type Icon Mapping
- `ranking_improved` → arrow-up / green tone
- `ranking_dropped` → arrow-down / red tone
- `new_review` → message icon / blue tone
- `negative_review` → alert icon / orange tone
- `rating_dropped` → star icon / red tone
- `competitor_overtake` → users icon / yellow tone
- `gbp_disconnected` → link-off icon / critical red tone

### Toast Notifications
- Renders assertive status content for new alerts.
- Opens detail view via CTA.
- Auto-dismisses after 5 seconds by default.

## API Contract Assumptions
Tests align to TASK-35-16 / `LocalSEOAlertResource`:
- list: `GET /api/v1/local-seo/alerts`
- unread count: `GET /api/v1/local-seo/alerts/unread-count`
- mark read: `POST /api/v1/local-seo/alerts/{id}/read`
- mark all read: `POST /api/v1/local-seo/alerts/mark-all-read`
- delete: `DELETE /api/v1/local-seo/alerts/{id}`
- location-scoped list: `GET /api/v1/locations/{id}/alerts`

Expected resource shape:
- `id`
- `type`
- `severity`
- `title`
- `message`
- `is_read`
- `read_at`
- `created_at`
- `location { id, name }`

## Important Implementation Note
The current backend resource does **not** expose a first-class `data` field for related details.

Because the task acceptance criteria mention “related data (e.g. ranking change details)”, the modal tests are written to require:
- **graceful rendering when related data exists**, and
- **no crash / no mandatory section when it does not**.

If Product wants related-data details to be guaranteed for all alert types, that likely requires a follow-up API expansion on top of TASK-35-16.
