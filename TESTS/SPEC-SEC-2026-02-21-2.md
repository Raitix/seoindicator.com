# Test Documentation: SPEC-SEC-2026-02-21-2 — Rotate APP_KEY and Configure GitHub Secrets

## Overview
Tests to verify APP_KEY rotation, GitHub Secrets configuration, and deployment workflow security.

## Test Type
- **Primary:** Integration Tests
- **Secondary:** Unit Tests

---

## Test Scenarios

### 1. APP_KEY Format Validation

**Test ID:** SEC-2.1  
**Type:** Unit  
**Priority:** Critical

**Description:** Verify APP_KEY has correct Laravel format (base64:encoded).

**Preconditions:**
- New APP_KEY generated

**Test Steps:**
1. Check APP_KEY starts with `base64:`
2. Verify base64 string is 32 bytes decoded (44 chars encoded)
3. Validate regex pattern: `^base64:[A-Za-z0-9+/]{42,44}={0,2}$`

**Expected Result:**
- APP_KEY matches Laravel format
- Decoded key is exactly 32 bytes

---

### 2. APP_KEY Not in Repository

**Test ID:** SEC-2.2  
**Type:** Integration  
**Priority:** Critical

**Description:** Verify new APP_KEY is not stored in any repository file.

**Preconditions:**
- APP_KEY rotated

**Test Steps:**
1. Extract APP_KEY from environment
2. Run `git grep -f` with the key value
3. Search all branches and tags

**Expected Result:**
- No files contain the APP_KEY value
- Key only exists in `.env` (ignored) and GitHub Secrets

---

### 3. GitHub Secrets Configured

**Test ID:** SEC-2.3  
**Type:** Integration  
**Priority:** Critical

**Description:** Verify GitHub Secrets are properly configured.

**Preconditions:**
- Repository has GitHub Actions workflow

**Test Steps:**
1. Check `LARAVEL_APP_KEY` secret exists
2. Check `DB_PASSWORD` secret exists
3. Verify secrets are referenced in workflow

**Expected Result:**
- Required secrets present in repository settings
- Secrets not exposed in logs

**Note:** Manual verification required in GitHub UI as API access may not be available.

---

### 4. deploy.yml Uses Secrets

**Test ID:** SEC-2.4  
**Type:** Unit  
**Priority:** Critical

**Description:** Verify deployment workflow references secrets correctly.

**Preconditions:**
- `.github/workflows/deploy.yml` exists

**Test Steps:**
1. Parse deploy.yml file
2. Find `${{ secrets.LARAVEL_APP_KEY }}` reference
3. Find `${{ secrets.DB_PASSWORD }}` reference
4. Verify no hardcoded values

**Expected Result:**
```yaml
env:
  APP_KEY: ${{ secrets.LARAVEL_APP_KEY }}
  DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
```

---

### 5. Local .env Has New APP_KEY

**Test ID:** SEC-2.5  
**Type:** Unit  
**Priority:** High

**Description:** Verify local `.env` file contains the new APP_KEY.

**Preconditions:**
- APP_KEY rotation completed

**Test Steps:**
1. Read `.env` file
2. Extract APP_KEY value
3. Compare with generated key

**Expected Result:**
- `.env` contains new APP_KEY
- Application boots without errors

---

### 6. Session Invalidation After Rotation

**Test ID:** SEC-2.6  
**Type:** Integration  
**Priority:** High

**Description:** Verify all existing sessions are invalidated after APP_KEY rotation.

**Preconditions:**
- Application had active sessions
- APP_KEY was rotated

**Test Steps:**
1. Create a session before rotation
2. Rotate APP_KEY
3. Attempt to use old session token
4. Verify session is invalid

**Expected Result:**
- Old session tokens fail validation
- Users must re-authenticate

## Security Considerations

### Adversarial Testing
- Test that old APP_KEY cannot decrypt new sessions
- Test for timing attacks on key comparison
- Verify key is not logged in error reports

### Production Impact Warning
⚠️ **APP_KEY rotation invalidates all sessions and encrypted data.**

Before running in production:
1. Notify all users of upcoming logout
2. Schedule during low-traffic period
3. Have rollback plan ready
