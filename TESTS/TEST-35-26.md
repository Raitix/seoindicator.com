# TEST-35-26 — Production SPA Auth Persistence for Local SEO Protected Routes

## Task Reference
- Task: `TASK-35-26`
- Spec: `SPEC-035` — Local SEO & Google Business Profile Tracking
- Stage: PreTester
- Status after test design: `To Develop`

## Overview
Production login now reaches the backend correctly and returns a bearer token, but the SPA still loses auth on protected Local SEO routes because `AuthContext` re-checks `/api/v1/auth/user`, receives an unauthenticated result, and clears the locally stored user state.

This test pack locks down the **token-backed SPA fallback contract** for the deployed static frontend:
- login/register persist the returned bearer token
- logout clears that persisted fallback state cleanly
- `AuthContext` does **not** immediately throw the user back to `/login` on protected Local SEO routes when a valid persisted SPA auth state already exists
- protected-route hydration and later user refreshes keep the stored user alive until the chosen fallback contract is explicitly torn down

## Chosen Auth Contract for This Task
This task chooses the **documented localStorage/bearer fallback** path as the required production contract.

Rationale:
- production `POST /api/v1/auth/login` already returns a bearer token
- the static frontend is already persisting `seoindicator_user`
- Local SEO protected fetches already include bearer token fallback after TASK-35-25
- the remaining blocker is that `AuthContext` still treats `/auth/user` as the sole source of truth and clears local auth too aggressively

If the Developer instead wants cookie/session auth to become the single source of truth, they must make that contract fully work in production and update docs/config accordingly. The tests written here intentionally enforce the bearer fallback path because that is the currently shipped behavior exposed by the API.

## Test Scenarios

### Auth API Routing / Storage Contract
| ID | Scenario | Expected |
|---|---|---|
| APR-001 | `fetchUser()` with configured backend origin | hits `{origin}/api/v1/auth/user` |
| APR-002 | `login()` | fetches Sanctum CSRF from `{origin}/sanctum/csrf-cookie` |

| APR-004 | `register()` | posts to `{origin}/api/v1/auth/register` |
| APR-005 | `register()` success with token | stores `seoindicator_token` |
| APR-006 | `fetchUser()` with persisted token | sends `Authorization: Bearer ...` |
| APR-007 | `logout()` with persisted token/user | posts to `{origin}/api/v1/auth/logout` and clears persisted fallback auth state |

### AuthContext Protected-Route Persistence
| ID | Scenario | Expected |
|---|---|---|
| ACP-001 | Protected route mount with stored user + stored bearer token + `fetchUser()` returning unauthenticated/null | user remains authenticated, provider does not redirect to `/login` |

| ACP-003 | Protected route mount with no stored fallback auth state | redirect to `/login` still happens |

## Expected Current Outcome
Red phase.

Current `AuthContext` behavior still clears local auth when `fetchUser()` resolves `null`:
- during initial hydration
- during `refreshUser()`

That means a token-backed SPA session can already exist, but the provider still destroys it before `/sites/{siteId}/local` has a chance to use the bearer-backed protected fetches.

## Developer Notes
1. Do **not** treat `/api/v1/auth/user` as the only truth source when a stored bearer-backed SPA session already exists.
2. Preserve local auth state on protected-route hydration when the chosen fallback contract is active.
3. Keep Local SEO protected fetches aligned with the same fallback contract.
4. If switching away from the bearer fallback contract, update production docs/config and make the cookie/session contract fully pass end-to-end instead.
