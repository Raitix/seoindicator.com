Incremental Indicator Processing – Implementation Plan

Purpose
- Deliver results row-by-row after submit, improving perceived speed and UX.
- Avoid a full framework rewrite; keep PHP + Bootstrap with minimal JS.
- Maintain compatibility with shared hosting (Hostinger).

High-level Approach (simplified)
1) Create job and seed results as Pending.
2) Run each indicator via JSON endpoints; update rows as they complete.
3) Show table immediately after submit (no blocking spinner).

Milestones & Deliverables
M1: Data model + endpoints scaffold  [DONE]
M2: Indicator execution refactor with shared context reuse  [PENDING]
M3: Frontend JS orchestration + progressive UI updates  [PARTIAL]
M4: Quota/rate-limiting strategy, error handling, and logging  [PARTIAL]
M5: Final QA, performance hardening, and rollout  [PENDING]

1) Database Changes (Job Store)
Goal: Avoid PHP session lock contention; enable multi-request concurrency; persist progress.

Tables
- jobs
  - job_id VARCHAR(64) PRIMARY KEY
  - session_id VARCHAR(128) NOT NULL
  - domain VARCHAR(255) NOT NULL
  - normalized_domain VARCHAR(255) NULL
  - final_url VARCHAR(2048) NULL
  - page_content MEDIUMTEXT NULL
  - created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  - updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
  - cancelled TINYINT(1) DEFAULT 0

- job_results
  - job_id VARCHAR(64) NOT NULL
  - indicator VARCHAR(64) NOT NULL
  - status ENUM('pending','running','done','error') NOT NULL DEFAULT 'pending'
  - score TINYINT NULL
  - details MEDIUMTEXT NULL
  - suggestion MEDIUMTEXT NULL
  - error TEXT NULL
  - duration_ms INT NULL
  - updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
  - PRIMARY KEY(job_id, indicator)
  - INDEX(job_id)

SQL (MySQL)
- Create tables (adjust engine/charset as needed):
  CREATE TABLE jobs (
    job_id VARCHAR(64) PRIMARY KEY,
    session_id VARCHAR(128) NOT NULL,
    domain VARCHAR(255) NOT NULL,
    normalized_domain VARCHAR(255) NULL,
    final_url VARCHAR(2048) NULL,
    page_content MEDIUMTEXT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    cancelled TINYINT(1) DEFAULT 0
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

  CREATE TABLE job_results (
    job_id VARCHAR(64) NOT NULL,
    indicator VARCHAR(64) NOT NULL,
    status ENUM('pending','running','done','error') NOT NULL DEFAULT 'pending',
    score TINYINT NULL,
    details MEDIUMTEXT NULL,
    suggestion MEDIUMTEXT NULL,
    error TEXT NULL,
    duration_ms INT NULL,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY(job_id, indicator),
    KEY idx_job_id(job_id)
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

Notes
- job_id can be a UUIDv4 string.
- Consider a retention policy (e.g., purge jobs older than 24–48h).

2) Backend Endpoints (PHP, JSON)
Goal: Decouple orchestration into small, fast endpoints suited for shared hosting.

Endpoints  [PARTIAL DONE]
- POST /api/start-analysis.php
  - Input: domain (string)
  - Logic: validate + rate-limit (1/min/IP; continue using existing policy but only here), create job, normalize domain, resolve final accessible URL, fetch page once, store page_content + final_url + 17 pending results.
  - Output: { job_id, indicators: [17 keys], final_url }  [DONE]

- POST /api/run-indicator.php
  - Input: job_id (string), indicator (string)
  - Logic: validate session ownership and job not cancelled; load job; set status=running; build shared context (reuse stored page_content and final_url; parse DOM on-demand or cache parsed artifacts); run exactly one indicator; save {score, details, suggestion}; set status=done or error.
  - Output: { job_id, indicator, status, score, details, suggestion }

- GET /api/job-progress.php?job_id=...  [DONE]
  - Input: job_id (string)
  - Logic: return array of 17 indicators with status/score; compute and return current overall score snapshot.
  - Output: { job_id, results: { [indicator]: {status, score, details?} }, overall }

- POST /api/cancel-job.php  [DONE]
  - Input: job_id
  - Logic: mark jobs.cancelled=1; further run-indicator calls should bail fast.
  - Output: { job_id, cancelled: true }

Implementation Notes
- Return JSON only; set proper headers; consistent error structure.
- Use session_write_close() after validating session to avoid session-locking across concurrent subcalls.
- Guard with CSRF token or a short-lived job_token stored in session.

4) Frontend Orchestration (index.php + JS)
Goal: Show table immediately; update rows progressively.

UI/UX
- Keep PRG flow. After redirect to results-view, inject a JS bootstrap:
  - Call /api/start-analysis.php with the submitted domain.
  - Receive { job_id, indicators } and render table rows as “Pending…”.
  - Maintain a throttled queue (e.g., max 5 concurrent) to POST /api/run-indicator.php per indicator.
  - On each completion, update that row: stars via small client-side helper, set details/suggestion, and class color (success/warning/danger) aligned with get_score_row_class mapping.
  - Update a top progress bar (completed/17) and recompute Overall score incrementally (either by simple weighted formula on client or by polling /api/job-progress.php every 1–2s).
  - (Optional) Retry/Cancel controls.

JS Implementation Notes  [PARTIAL]
- Add a small star-render helper to mirror server’s 1–3 mapping. Keep CSS consistent.
- Throttle concurrency to 4–6 to protect the host and OpenRouter/PageSpeed quotas.
- Display durations and errors succinctly; keep UX snappy.

---
5) Rate Limiting & Quotas
- Enforce 1 req/min/IP on start-analysis only; subcalls authorized via job/session.  [DONE]
- Validate job ownership via session_id or a job_token.
- Consider delaying/PageSpeed to end or behind a toggle.
- Optionally cap AI calls: only execute AI if static checks meet minimal criteria.

---
6) Security
- Input validation: domain normalization and allowlist protocol (http/https).
- Tie job_id to user session; deny cross-session access.
- CSRF protection: token on start-analysis; send with subcalls.
- Output sanitization: only allow HTML for the current allowed indicators; escape everywhere else.
- DoS protection: throttle concurrent run-indicator calls per job; enforce short timeouts.

---
7) Error Handling & Resilience
- Per-indicator timeout (10–15s) and single retry for transient network errors.
- Mark rows as error with a short reason; allow manual retry.
- If base page fetch fails, apply current dev flag behavior (mock non-title) but clearly label the state; consider disabling mock for production once stable.

---
8) Logging & Observability
- Log per-indicator duration, external API response codes, and failures.
- Add job summary logs (completed count, total duration, cancellations).
- Create a simple admin view or SQL queries for monitoring top errors.

---
9) Performance & Caching
- Reuse fetched page_content + parsed DOM across all indicators.
- Optional: cache results per domain for N minutes; immediately show cached while refreshing in background.
- Keep payloads small; return only necessary fields in JSON.

11) Testing Plan
- Unit-test indicator functions with representative HTML fixtures (title/meta/404/mobile/etc.).
- Integration: end-to-end job flow with a test domain; verify progressive updates and overall score.
- Negative tests: unreachable domain, robots/sitemap 404s, invalid canonical, missing meta, AI/API timeouts.
- Quota tests: simulate many concurrent jobs; verify throttling and no host overload.
- Cross-browser sanity (Chrome/Firefox/Edge) for the JS updates.

---
12) Acceptance Criteria
- User sees first results within 1–3 seconds for reachable sites.
- Table rows update progressively; progress bar reflects accurate counts.
- Overall score updates at least every 1–2 seconds or after each row completes.
- Cancel stops remaining work within 1 second and no further external calls are made.
- Errors are visible per row with retry available.
- No session lock contention under concurrent subcalls.
